# yourmate — MVP Design & Architecture

This document turns [REQUIREMENTS.md](REQUIREMENTS.md) into a concrete technical plan:
what pieces exist, what the database looks like, what the API offers, and how the
app's screens fit together. It is the blueprint we code against.

## 1. System Overview

Three pieces talk to each other:

```
   ┌─────────────────────┐        HTTPS / JSON        ┌──────────────────────┐
   │   Mobile app        │  ───────────────────────►  │   API server         │
   │   React Native      │                            │   Node.js + Express  │
   │   + Expo            │  ◄───────────────────────  │   (TypeScript)       │
   │   (TypeScript)      │      JSON responses        └──────────┬───────────┘
   └─────────────────────┘                                       │ SQL (pg)
                                                                 ▼
                                                      ┌──────────────────────┐
                                                      │   PostgreSQL         │
                                                      └──────────────────────┘
```

**Key principle:** the mobile app never touches the database directly. It only ever
calls the API server, and the API server is the only thing holding database
credentials. All rules ("is this person allowed to delete this task?") live on the
server, because anything enforced only in the app can be bypassed.

### Chosen stack (from the requirements phase)

| Concern | Choice |
|---|---|
| Language (both sides) | TypeScript |
| App framework | React Native + Expo |
| Navigation | React Navigation |
| Data fetching | `fetch()` wrapped in custom hooks (no data library) |
| Server | Node.js + Express |
| Database access | Raw SQL via the `pg` library |
| Auth | JWT bearer tokens, `bcrypt`-hashed passwords |
| Scheduled jobs | `node-cron` inside the server process |

## 3. Database Schema

Five tables. IDs are UUIDs (generated by Postgres) rather than counting numbers, so
they can't be guessed or enumerated through the API.

```sql
-- 001_init.sql

CREATE EXTENSION IF NOT EXISTS pgcrypto;   -- provides gen_random_uuid()

-- ─── users ────────────────────────────────────────────────────────────────
CREATE TABLE users (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email          TEXT NOT NULL UNIQUE,          -- always stored lower-cased
  password_hash  TEXT NOT NULL,                 -- bcrypt, never the raw password
  display_name   TEXT NOT NULL,
  bio            TEXT,
  avatar_data    BYTEA,                         -- profile picture bytes
  avatar_mime    TEXT,                          -- e.g. 'image/jpeg'
  holiday_mode   BOOLEAN NOT NULL DEFAULT FALSE,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ─── environments (households) ────────────────────────────────────────────
CREATE TABLE environments (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name         TEXT NOT NULL,
  invite_code  TEXT NOT NULL UNIQUE,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ─── memberships (which users are in which environments) ──────────────────
CREATE TABLE memberships (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  environment_id  UUID NOT NULL REFERENCES environments(id) ON DELETE CASCADE,
  role            TEXT NOT NULL CHECK (role IN ('owner', 'member')),
  joined_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, environment_id)
);

CREATE INDEX idx_memberships_environment ON memberships(environment_id, joined_at);

-- ─── tasks ────────────────────────────────────────────────────────────────
CREATE TABLE tasks (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  environment_id      UUID NOT NULL REFERENCES environments(id) ON DELETE CASCADE,
  short_description   TEXT NOT NULL,
  long_description    TEXT,
  deadline            DATE NOT NULL,
  frequency           TEXT NOT NULL
                        CHECK (frequency IN ('one_off','daily','weekly','monthly')),
  frequency_interval  INT NOT NULL DEFAULT 1,   -- "every N weeks"; 1 for the rest
  assignment_type     TEXT NOT NULL
                        CHECK (assignment_type IN ('rotational','manual','unassigned')),
  assigned_user_id    UUID REFERENCES users(id) ON DELETE SET NULL,
  status              TEXT NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending','done')),
  completed_at        TIMESTAMPTZ,              -- when it was last marked done
  completed_by        UUID REFERENCES users(id) ON DELETE SET NULL,
  created_by          UUID REFERENCES users(id) ON DELETE SET NULL,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),  -- "date added"
  -- added in 002: rotation landed back on the completer because everyone else
  -- is on holiday (see Section 6.2)
  assigned_while_covering BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE INDEX idx_tasks_environment ON tasks(environment_id, status, deadline);

-- ─── notifications ────────────────────────────────────────────────────────
-- One row per recipient, so "read" status is tracked per person.
CREATE TABLE notifications (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  environment_id  UUID NOT NULL REFERENCES environments(id) ON DELETE CASCADE,
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,  -- recipient
  actor_id        UUID REFERENCES users(id) ON DELETE SET NULL,          -- who acted
  task_id         UUID REFERENCES tasks(id) ON DELETE CASCADE,
  type            TEXT NOT NULL CHECK (type IN (
                    'task_created','task_completed','task_claimed',
                    'task_reassigned','member_joined','member_left')),
  message         TEXT NOT NULL,      -- pre-built readable text
  read_at         TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_notifications_user ON notifications(user_id, environment_id, created_at DESC);
```

### Schema notes & decisions

- **Roles live on `memberships`, not `environments`.** A user's role is per-household
  (owner of one, member of another), exactly as the requirements state, and one query
  answers both "is this person in this household?" and "what can they do?".
- **`joined_at` drives rotation order.** Rotational tasks cycle in join order, so this
  column is load-bearing, not just informational.
- **`deadline` is a `DATE`, not a timestamp** (confirmed). Household tasks are
  day-granular ("bins out Tuesday"), and dropping the time component avoids an entire
  category of timezone bugs.
- **`ON DELETE CASCADE`** means deleting an environment automatically deletes its
  memberships, tasks, and notifications — no orphaned rows to clean up by hand.
- **Profile pictures are stored in the database** (`avatar_data`), per the requirements
  decision to avoid needing a cloud storage account. The server will enforce a size cap
  (suggest ~1 MB, resized client-side before upload).

## 4. Authentication Design

1. **Sign up** — server lower-cases the email, hashes the password with bcrypt, inserts
   the user, returns a JWT.
2. **Log in** — server looks up by email, `bcrypt.compare`s the password, returns a JWT.
3. The app stores the token in **Expo SecureStore** (encrypted device storage, not plain
   `AsyncStorage`).
4. Every subsequent request sends `Authorization: Bearer <token>`.
5. `middleware/auth.ts` verifies the token and attaches `req.userId`. Any route that
   needs a logged-in user goes through it.
6. **Log out** is client-side only: delete the stored token. (Stateless JWTs need no
   server call.)

### The permission pattern that matters most

Being logged in is not the same as being allowed. Every environment-scoped route must
also check membership, or any user could read another household's tasks just by
guessing an ID:

```ts
// services/membership.ts
// Returns the caller's role, or throws 403 if they aren't in this environment.
async function requireMembership(userId: string, environmentId: string): Promise<Role>

// Throws 403 unless the caller is the owner.
async function requireOwner(userId: string, environmentId: string): Promise<void>
```

For task routes, the check is: load the task → find its `environment_id` → require
membership in *that* environment.

## 5. API Endpoints

All routes return JSON. All except `/auth/*` require a bearer token.

### Auth
| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/signup` | `{ email, password, displayName }` → `{ token, user }` |
| POST | `/auth/login` | `{ email, password }` → `{ token, user }` |

### Profile
| Method | Path | Purpose |
|---|---|---|
| GET | `/me` | Current user's profile |
| PATCH | `/me` | Update `displayName`, `bio`, and/or `holidayMode` |
| PUT | `/me/avatar` | Upload/replace profile picture |
| GET | `/users/:id/avatar` | Serve a user's picture as an image |

### Environments
| Method | Path | Purpose |
|---|---|---|
| GET | `/environments` | My environments + a task summary count each (dashboard) |
| POST | `/environments` | `{ name }` → creates it, caller becomes owner |
| POST | `/environments/join` | `{ inviteCode }` → join an existing environment |
| GET | `/environments/:id` | Detail: name, invite code, members, my role |
| PATCH | `/environments/:id` | Rename — **owner only** |
| DELETE | `/environments/:id` | Delete environment — **owner only** |
| POST | `/environments/:id/invite-code` | Regenerate invite code — **owner only** |
| GET | `/environments/:id/members` | Member list, in join order |
| DELETE | `/environments/:id/members/:userId` | Owner removes a member, or a member leaves (self) |

### Tasks
| Method | Path | Purpose |
|---|---|---|
| GET | `/environments/:id/tasks` | Task list for the environment |
| POST | `/environments/:id/tasks` | Create a task |
| GET | `/tasks/:id` | Full task detail (incl. long description) |
| PATCH | `/tasks/:id` | Edit any field |
| DELETE | `/tasks/:id` | Delete a task |
| POST | `/tasks/:id/complete` | Mark done → triggers recurrence + rotation (Section 6) |
| POST | `/tasks/:id/claim` | Take ownership of an unassigned task |

### Notifications
| Method | Path | Purpose |
|---|---|---|
| GET | `/environments/:id/notifications` | Feed for this environment |
| POST | `/environments/:id/notifications/read` | Mark the feed as read |

**Invite codes:** 6 characters, uppercase, drawn from an alphabet that excludes
look-alikes (`0`/`O`, `1`/`I`/`L`) so they're easy to read aloud and type. Generated on
creation, regenerable by the owner (which invalidates the old one).

## 6. Core Business Logic

These three rules are the genuinely tricky part of the app and live in `services/`,
not inside route handlers, so they can be tested on their own.

### 6.1 Completing a task

```
POST /tasks/:id/complete
  │
  ├─ frequency = 'one_off'
  │     └─► status = 'done', completed_at = now(), completed_by = caller
  │         (app greys it out; the cleanup job deletes it next week)
  │
  └─ frequency = daily | weekly | monthly
        ├─► deadline  = nextDeadline(deadline, frequency, interval)
        ├─► assignee  = rotational ? nextAssignee(...) : unchanged
        └─► status stays 'pending'  (completed_at/by record the last completion)
```

### 6.2 Rotation (`services/rotation.ts`)

When a **rotational** task is completed:

1. Load members ordered by `joined_at ASC` (tie-break on `id` for stability).
2. Find the current assignee's position in that list.
3. Walk forward from there, wrapping around to the start, and pick the **first member
   whose `holiday_mode` is `false`** — this implements the "holiday mode skips your
   turn" requirement.
4. If that walk finds nobody at all (**everyone** is on holiday, the completer
   included), fall back to the **next member in plain join order**, holiday or not.
   The task then **stays with that person until they turn holiday mode off or leave** —
   it is not re-rotated in the meantime. It deliberately does *not* go back to the
   completer.

In pseudocode:

```
nextAssignee(members, completerId):
  ordered = members sorted by joined_at
  start   = index of completerId in ordered

  for step in 1..ordered.length:                    # wraps all the way round
    candidate = ordered[(start + step) % length]
    if not candidate.holidayMode:
      return { assignee: candidate,
               covering: candidate.id == completerId and length > 1 }

  return { assignee: ordered[(start + 1) % length], covering: false }
```

**The "covering" case.** When the loop wraps the whole way round and lands back on the
person who just completed the task, it means every housemate is away and they are the
only one home. They keep the task — chores shouldn't stall while someone is there to do
them — but the assignment is **flagged as covering** so the app can say so explicitly
rather than silently handing them every chore. Stored as `tasks.assigned_while_covering`
and recalculated on each completion, so it clears itself once housemates return.

`covering` is false in a **one-person household** (`length > 1` guard): with nobody else
in the flat you aren't covering for anyone, the task simply returns to you.

Note all of this is computed **at completion time**, not stored as a schedule. Turning
holiday mode on affects the *next* rotation, not one already assigned to you.

### 6.3 Recurrence (`services/recurrence.ts`)

| Frequency | Next deadline |
|---|---|
| `daily` | previous deadline + 1 day |
| `weekly` | previous deadline + (7 × `frequency_interval`) days |
| `monthly` | previous deadline + 1 month |

Two rules that prevent real bugs:

- **Advance from the old deadline, then catch up.** If a task was overdue by three
  weeks, adding one week to its old deadline still lands in the past. So keep advancing
  until the new deadline is in the future. This keeps repeating tasks on their original
  rhythm (bins are always due Tuesday) instead of drifting.
- **Month-end clamps** (confirmed). Postgres's `+ INTERVAL '1 month'` turns Jan 31 into
  Feb 28 (or 29). It then stays on the 28th in following months rather than jumping back
  to the 31st.

### 6.4 Weekly cleanup (`jobs/cleanupTasks.ts`)

Per the requirements, completed one-off tasks grey out until the end of the week, then
are deleted before the next week starts.

```sql
DELETE FROM tasks
WHERE frequency = 'one_off'
  AND status = 'done'
  AND completed_at < date_trunc('week', now());
```

`date_trunc('week', ...)` treats **Monday** as the start of the week in Postgres, which
matches the ISO week decision in the requirements.

**Scheduling:** run this **daily** rather than only on Mondays. The condition is
self-correcting — anything completed before the current week goes, whenever the job
runs — so a server that was down on Monday still cleans up on Tuesday. A once-weekly
job would silently skip that week.

### 6.5 Notifications (`services/notify.ts`)

When one of the six event types happens, write one row **per recipient**, excluding the
person who performed the action (you don't get notified of your own doing).

**Holiday mode + notifications (confirmed).** Notification rows are **always written**,
including for users in holiday mode — but while holiday mode is on they **don't count
toward the unread badge**. The feed stays quiet while you're away, and you can catch up
on what you missed when you return.

This preserves history, is reversible, and is the behaviour that still makes sense once
real push notifications are added later (mute the push, keep the feed entry).

## 7. App Screen Flow

```
App launch
  └─ Is there a saved token in SecureStore?
       │
       ├─ No ──► Auth Stack
       │            ├─ LoginScreen
       │            └─ SignUpScreen
       │
       └─ Yes ─► Main Tabs
                    │
                    ├─ 🏠 Home (stack)
                    │     ├─ DashboardScreen
                    │     │     ├─ (no environments) → EmptyStateScreen
                    │     │     │        ├─ CreateEnvironmentScreen
                    │     │     │        └─ JoinEnvironmentScreen  (invite code)
                    │     │     └─ (has environments) → list of environment cards
                    │     │
                    │     └─ EnvironmentScreen          ← tap an environment
                    │           │  (task list; 🔔 bell in header)
                    │           ├─ TaskDetailScreen      → edit / complete / delete
                    │           ├─ TaskFormScreen        → create & edit
                    │           ├─ MembersScreen         → members, invite code, owner actions
                    │           └─ NotificationsScreen   ← the 🔔 bell
                    │
                    └─ 👤 Profile (stack)
                          ├─ ProfileScreen         → picture, bio, holiday mode toggle
                          └─ EditProfileScreen
```

**Why notifications aren't their own tab:** the requirements scope the feed *per
environment*, so it belongs behind a bell icon inside an environment rather than as a
global list mixing households together.

### Data fetching pattern

Since we're using plain `fetch` (no caching library), each screen follows one small,
repeatable shape — a custom hook returning data plus loading/error state and a
`refetch` function:

```ts
const { data: tasks, loading, error, refetch } = useTasks(environmentId);
```

After any change (create, edit, complete, delete), the screen calls `refetch()` to pull
fresh data. That explicit refetch is the manual step React Query would have automated —
easy to follow, but easy to *forget*, so it's the first place to look if a list ever
looks stale.

## 8. Local Development Setup

| Piece | How it runs |
|---|---|
| PostgreSQL | Locally on your Mac (Postgres.app or Homebrew), database `yourmate_dev` |
| API server | `npm run dev` in `server/` → `http://localhost:3000` |
| Mobile app | `npx expo start` in `app/` → iOS Simulator, or Expo Go on your phone |

**The one gotcha:** `localhost` on a phone means *the phone itself*, not your Mac. The
iOS Simulator can use `http://localhost:3000`, but a real device on the same Wi-Fi must
use your Mac's LAN address (e.g. `http://192.168.1.20:3000`). The API base URL will
live in one config value so this is a one-line change.

Secrets (`DATABASE_URL`, `JWT_SECRET`) go in `server/.env`, which is git-ignored;
`.env.example` documents the required names without real values.

**Deployment is out of scope for the MVP build phase** — everything runs locally while
we develop. Hosting (e.g. Railway or Render for the server and database) comes later,
once the app works end to end.

## 9. Build Order

A sequence where each step is testable before the next one depends on it:

1. ✅ **Database** — write and run `001_init.sql`; confirm tables exist.
2. ✅ **Server skeleton** — Express + `pg` connection + a health-check route.
3. ✅ **Auth** — signup/login/JWT + the auth middleware.
4. ✅ **Environments** — create, join, list, members, roles.
5. ✅ **Tasks** — CRUD, then complete/claim with rotation + recurrence.
6. ✅ **Notifications** — event writing and the feed endpoints.
7. ✅ **Cleanup job** — the weekly deletion cron.
8. **App: auth screens** — login/signup, token storage, the logged-in/out split.
9. **App: dashboard + environments** — empty state, create, join.
10. **App: tasks** — list, detail, create/edit form, complete.
11. **App: profile + notifications** — picture, bio, holiday mode, feed.

Tests live in `server/tests/` and run with `npm test` (Node's built-in test runner via
`tsx`). Each test file runs in its own process against the shared dev database, so each
one scopes its accounts to its own email sub-domain to avoid tripping over the others.

Steps 1–7 give a working API testable entirely with `curl` before any UI exists, which
keeps app debugging from being tangled up with backend debugging.

## 10. Decisions Log

All four points raised during design have been confirmed:

1. **Deadlines are date-only** (no time of day) — Section 3.
2. **All members in holiday mode** → the task passes to the next member in join order
   regardless, never back to whoever just completed it, and stays with them until they
   come off holiday or leave — Section 6.2.
3. **Month-end clamping**: Jan 31 → Feb 28, and it stays on the 28th thereafter —
   Section 6.3.
4. **Holiday mode notifications**: rows are always written but don't count toward the
   unread badge while holiday mode is on — Section 6.5.

5. **Completer is the only person home** (others on holiday, but not all): the task
   returns to them rather than stalling, and is flagged as `covering` so the app can
   show that they're picking up the slack — Section 6.2.

No open points remain.
